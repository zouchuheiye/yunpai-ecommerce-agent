# 统筹 Agent 否定式只读请求修复设计

## 背景

谢良璇在 PR #9 提交 `adee44e` 的真实 DeepSeek 人工测试中确认：

- `只查询商品 ...，不修改任何数据` 被错误要求确认写操作（STD-02）。
- `只读检查知识库和 SOP ...，不修改或审批任何内容` 被错误要求确认写操作（STD-04）。
- 去掉否定式安全说明后，相同只读查询能够正常执行。

根因是统筹入口的确定性写操作门禁只检查动作词是否出现，没有识别动作词是否处于明确否定作用域。通用高风险动作检测和统筹入口补充正则都会把否定句中的 `修改`、`审批` 等词当作真实写入意图。

## 目标

只在统筹 Agent 入口修复明确否定的写动作识别，同时保持真实写操作继续进入人工确认门禁。

## 行为契约

以下请求属于只读，不应因否定短语触发确认：

- `只查询商品价格，不修改任何数据`
- `只读检查知识库和 SOP，不修改或审批任何内容`
- `查看实验状态，不创建或修改实验`

以下请求仍属于写操作，必须触发确认：

- `直接修改商品价格`
- `不要只查询，直接修改商品价格`
- `不修改商品，但创建采购单`
- `查询后审批这些候选`

## 设计

在 `workspace_agent.py` 中增加一个只服务统筹入口的否定式动作清洗函数。它仅移除由 `不`、`不要`、`无需`、`无须`、`不必`、`不得`、`不能`、`不会`、`禁止` 明确修饰的写动作短语，再将剩余文本交给现有两层写操作检测。

清洗以分句和动作词为边界，不把整个请求标记为只读。因此混合请求中未被否定的动作仍会触发确认。现有全局 `policy.py` 不修改，避免改变客服、售后、评测和其他调用方的安全语义。

## 测试

采用 TDD：

1. 先为 STD-02、STD-04 和“不创建或修改实验”增加失败测试。
2. 增加真假混合表达测试，证明真实写操作仍被拦截。
3. 实现最小否定作用域清洗。
4. 运行统筹 Agent 专项、策略回归和邻接 API 回归。
5. 临时禁用清洗逻辑，确认 STD-02/STD-04 测试按预期失败；恢复后复验。

## 非目标

- 不修复订单字段提取或多轮上下文。
- 不修复质检、评测、自动派单事实映射。
- 不修改复合查询、会话持久化、数据库 Schema 或前端。
- 不降低真实写操作的人工确认要求。
